# 3일차 서버 배포와 랭킹 시스템 구현

작성일: 2026-10-30

이번 수업은 **3일차 02. 프로젝트 작업**까지 진행했다. 지난 시간에서 이어진 Unity 비동기 요청 실습과, 서버를 외부 URL로 호출하기 위한 배포 준비, 랭킹 시스템 구현을 정리한다. **03. 네트워크 데이터 흐름과 04. API 설계 실무는 아직 진행한 수업 범위에 포함하지 않는다.** 랭킹 구현을 위해 작성한 설계·API 메모는 이번 프로젝트 작업의 기록으로 다룬다.

## 오늘 배운 내용

### 기다리는 동안 Unity 화면을 계속 움직이게 하기

2일차 TIL을 작성했을 때는 Unity의 비동기 전환 실습을 다음 시간으로 미뤄 둔 상태였다. 현재 프로젝트에는 `MonsterClientAsync.cs`와 `AsyncFrameProbe.cs`가 있다.

- `await request.SendWebRequest()`는 네트워크 응답을 기다리는 동안 해당 비동기 메서드의 실행을 중단할 수 있다. 메인 스레드를 반복문으로 붙잡지 않으므로 Unity는 다음 프레임의 작업을 진행할 수 있다.
- 버튼에서 시작하는 `async void` 메서드 안에서는 `try/catch`로 실패를 처리하고, 실제 통신 메서드는 결과를 반환하는 `Task<T>` 등으로 분리한다.
- 요청 전에는 버튼을 비활성화하고, 성공·실패와 관계없이 `finally`에서 다시 활성화한다. 같은 요청이 여러 번 겹치는 것도 막는다.
- 코루틴은 `yield return`, 현재 프로젝트의 클라이언트는 `await`를 사용한다. 둘 다 무거운 계산을 자동으로 다른 스레드에 보내는 방식은 아니다.

`AsyncFrameProbe`는 `Task.Delay` 앞뒤의 프레임 번호와 스레드 ID를 기록하는 실험 코드다. 코드를 통해 실험 의도를 확인했으며, 이번 TIL 작성 중 Unity를 실행해 로그나 프레임 변화를 재측정하지는 않았다.

### GitHub에 올리는 것과 서버를 배포하는 것

GitHub는 소스와 변경 이력을 보관하는 곳이고, Render는 그 소스를 가져와 서버 프로세스를 실행하는 곳이다. `git push`가 성공했다고 새 API까지 실제 서비스에 반영됐다고 판단하면 안 된다.

```text
서버 코드 수정 → 커밋 → GitHub의 배포 대상 브랜치에 push
→ Render가 소스 가져오기 → Docker 이미지 빌드 → 컨테이너 실행
→ 공개 URL에서 응답 확인
```

자동 배포는 호스팅 서비스에 연결된 저장소·브랜치와 설정에 따라 동작한다. 기능 브랜치에 올린 코드는 그 브랜치가 배포 대상인지 별도로 확인해야 한다. 이번에는 랭킹 기능을 `RankSys`에 올렸으며, `main`에 병합하지 않았다. Render 대시보드의 실제 배포 브랜치와 자동 배포 설정은 이번 문서 작성 중 확인하지 않았다.

### 배포를 위해 서버 저장소를 분리했다

처음에는 서버와 Unity를 `ServerDataLearn` 한 저장소에서 관리했다. 이번에는 서버를 독립적으로 배포할 수 있도록 `GameDataServer`를 별도 저장소로 분리했다.

| 저장소 | 관리 대상 | 현재 역할 |
| --- | --- | --- |
| [ServerDataLearn](https://github.com/ssa25879/ServerDataLearn) | Unity 클라이언트, 실습 자료, TIL | 클라이언트와 수업 기록 관리 |
| [GameDataServer](https://github.com/ssa25879/GameDataServer) | ASP.NET Core 서버, 초기 데이터, Dockerfile | 서버 코드와 배포 구성 관리 |

로컬에서는 `GameDataServer` 폴더를 기존 위치에 두고 내부에 독립 Git 저장소를 만들었다. 상위 저장소에서는 `/GameDataServer/`를 제외하고 기존 추적도 해제했다. 폴더를 삭제한 것이 아니라 **같은 서버 파일을 두 저장소에서 중복 관리하지 않도록 관리 범위를 나눈 것**이다. 두 README에도 서로의 저장소 링크를 추가했다.

- `.gitignore`는 새 파일의 추적을 막는 규칙이다. 이미 추적하는 파일에는 규칙을 추가하는 것만으로 적용되지 않는다.
- `git rm --cached`는 로컬 파일을 남기면서 Git의 추적 대상에서 제외한다. 이후 커밋해야 저장소 이력에 반영된다.
- 서버의 `bin/`, `obj/`, `.vs/`, `*.user`, SQLite DB와 저널 파일은 제외한다. `app/`도 제외 규칙에 추가했다.
- `Data/monsters.json`은 초기 데이터로 관리하고, 실행하면서 만들어지는 `Data/game.db`는 관리하지 않는다.
- `.gitignore`의 `app/`는 로컬 Git 경로의 제외 규칙이다. Dockerfile의 `/app`은 컨테이너 내부 작업 경로이므로, 해당 규칙이 컨테이너의 `/app` 생성을 막지는 않는다.

### Dockerfile, 이미지, 컨테이너

| 구분 | 의미 | 이번 프로젝트에서의 예 |
| --- | --- | --- |
| Dockerfile | 이미지를 만드는 순서를 적은 파일 | SDK 준비, publish, 실행 명령 지정 |
| 이미지 | 실행 환경과 파일을 담은 결과물 | .NET 런타임과 서버 실행본 |
| 컨테이너 | 이미지를 바탕으로 실행 중인 환경 | `dotnet GameDataServer.dll` 프로세스 실행 |

현재 `GameDataServer/Dockerfile`은 빌드 단계와 실행 단계를 나눈다.

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /app .
ENTRYPOINT ["dotnet", "GameDataServer.dll"]
```

첫 단계의 SDK 이미지에서 코드를 빌드하고 실행본을 만든다. 두 번째 단계는 ASP.NET 런타임 이미지를 사용하며, 첫 단계의 실행본만 가져온다. 최종 실행 환경에는 빌드를 위한 SDK 전체가 필요하지 않다. `ENTRYPOINT`는 이미지를 만드는 순간 서버를 켜는 명령이 아니라, 컨테이너가 시작할 때 실행할 명령이다.

프로젝트 파일에는 `Data` 폴더의 파일을 출력 디렉터리로 복사하는 설정도 있다. 실행본만 옮기고 초기 데이터 파일을 빠뜨리지 않도록, publish 결과에도 필요한 파일이 있는지 확인해야 한다. 이번 TIL 작성에서는 Docker 이미지 빌드나 publish를 새로 실행하지 않았다.

### PORT와 0.0.0.0이 필요한 이유

현재 서버의 실행 설정은 다음과 같다.

```csharp
var port = Environment.GetEnvironmentVariable("PORT") ?? "5000";
app.Run($"http://0.0.0.0:{port}");
```

- `PORT`는 실행 환경이 프로세스 밖에서 전달하는 설정값이다. 값이 없으면 기본값 `5000`을 사용한다.
- `localhost`에만 바인딩하면 외부에서 컨테이너로 전달되는 요청을 받을 수 없는 구성이 될 수 있다. `0.0.0.0`은 모든 IPv4 인터페이스에서 연결을 기다리도록 지정한다.
- `0.0.0.0`은 클라이언트가 사용할 공개 주소가 아니다. 실제 외부 접근에는 서비스의 포트 연결, 네트워크·방화벽 설정과 공개 URL도 필요하다.
- Unity에서는 공개 HTTPS 주소로 요청한다. 다른 기기에서 `localhost`를 쓰면 서버 PC가 아니라 그 기기 자신을 가리킨다.

현재 로컬 `MonsterClientAsync.cs`에는 `https://gamedataserver-yws.onrender.com/monsters`가 지정되어 있다. 이 주소 변경은 아직 미커밋 상태이며, 실제 Unity 컴포넌트에는 Inspector에 저장된 값이 사용될 수 있으므로 소스의 기본값만 보고 연결 대상을 단정하면 안 된다.

### DB 파일의 유지와 배포 환경의 영속성

SQLite는 데이터를 파일에 저장하므로 같은 파일을 유지한 채 서버 프로세스만 재시작하면 저장값을 다시 읽을 수 있다. 하지만 컨테이너 내부 파일이 새 배포에서도 유지되는지는 별개의 문제다.

- DB를 Git에서 제외하는 것은 소스 관리 정책이다. 운영 데이터를 보관하는 방법까지 해결해 주지는 않는다.
- 컨테이너의 임시 파일 시스템에 DB를 두면 교체 과정에서 데이터를 잃을 수 있다. 영속 디스크나 외부 DB 등 저장 방식을 따로 결정해야 한다.
- 현재 코드는 콘텐츠 루트의 `Data/game.db`를 사용한다. 별도의 영속 저장 경로 설정은 아직 구현하지 않았다.
- 공개 URL은 비밀번호가 아니다. 현재 서버에는 인증 없이 데이터를 변경할 수 있는 API가 있으므로, 실제 서비스에서는 접근 제어도 별도로 설계해야 한다. HTTPS 사용만으로 호출자의 권한이 확인되지는 않는다.

## 프로젝트 작업 — 랭킹 시스템

### 과업 지시서에서 확인할 기준을 먼저 뽑기

수업의 랭킹 과제는 이름과 점수를 등록하고, SQLite에 저장한 뒤 상위 10명을 Unity에서 조회하는 것이다. 구현 순서는 **저장할 데이터 → API → 클라이언트 화면 → 배포 확인**으로 잡았다.

| 기준 | 확인할 동작 |
| --- | --- |
| A1 | 이름·점수를 보내면 저장된 값과 고유 번호를 201로 반환한다. |
| A2 | 빈 이름·음수 점수를 거절하고 400과 이유를 반환한다. |
| A3 | 점수 내림차순 상위 10명과 순위를 조회하고 Unity에 표시한다. |
| A4 | 같은 DB를 유지한 서버 재시작 후 점수가 남는다. |
| A5 | 배포 주소에서 등록·조회하고 다른 기기에서도 같은 랭킹을 본다. |

API 코드를 작성하는 것과 위 기준을 실제로 만족하는 것은 다르다. 특히 Unity 화면 확인, HTTP 응답 확인, 외부 배포 확인은 따로 기록해야 한다.

### 강의 예제와 현재 구현의 차이

수업의 예제 코드를 그대로 사용한 것은 아니다. 현재 프로젝트는 별도로 정한 **이름별 최고 점수 유지** 정책을 반영했다.

| 항목 | 강의 예제 | 현재 `RankSys` 구현 |
| --- | --- | --- |
| 이름 필드 | `player` | `name` |
| DB 열 | `id`, `player`, `score`, `created_at` | `id`, `name`, `score` |
| 같은 이름 재등록 | 점수 기록을 새 행으로 추가 | 기존 최고 점수를 유지하거나 갱신 |
| 조회 개수 | `?top=`으로 지정, 1~100으로 제한 | 최대 10명 고정 |
| 동점 순서 | 등록 id 오름차순 | 최초 등록 id 오름차순 |
| Unity 스크립트 | `ScoreClient.cs` | `RankingClient.cs` |

강의 예제의 `player` JSON을 현재 서버에 그대로 보내면 `name`이 없으므로 거절된다. `?top=3`을 붙여도 현재 구현의 조회 개수는 3명으로 바뀌지 않는다. 다른 사람의 서버와 함께 실습하려면 주소뿐 아니라 요청·응답 규격과 정책도 맞춰야 한다.

### 현재 서버의 저장과 조회

`scores` 테이블은 이름을 고유하게 관리하고 음수 점수를 허용하지 않는다. 같은 이름이 등록되면 최고 점수만 유지한다.

```sql
INSERT INTO scores (name, score) VALUES ($name, $score)
ON CONFLICT(name) DO UPDATE SET score = MAX(scores.score, excluded.score)
RETURNING id, name, score;
```

사용자 입력은 `$name`, `$score` 파라미터로 전달한다. 갱신해도 기존 id를 유지하므로, 동점일 때 최초 등록 순서를 계속 사용할 수 있다.

```sql
SELECT id, name, score
FROM scores
ORDER BY score DESC, id ASC
LIMIT 10;
```

읽은 순서대로 `1, 2, 3…` 순위를 붙인다. 공동 순위를 부여하는 방식은 아니다. 응답 예시는 현재 코드의 규격을 설명하기 위한 것으로, 아래 값 자체를 실제 배포 서버에서 받은 것은 아니다.

| 요청 | 성공 응답 | 잘못된 입력 |
| --- | --- | --- |
| `POST /scores` + `{ "name": "플레이어1", "score": 1200 }` | 201 + `{ "id": 1, "name": "플레이어1", "score": 1200 }` | 400 + `{ "error": "이유" }` |
| `GET /scores` | 200 + `{ "scores": [{ "rank": 1, "id": 1, "name": "플레이어1", "score": 1200 }] }` | 별도 조회 매개변수 없음 |

POST는 이름 앞뒤 공백을 제거하고 빈 이름, 누락된 점수, 음수, 정수가 아닌 값 등을 검사한다. 정상적인 `0점`과 `score` 필드 누락을 구분하는 것도 필요하다. 이미 등록한 이름에 같거나 낮은 점수를 보내도 유효한 요청이면 201과 최종 저장된 최고 점수를 반환한다.

### Unity 클라이언트와 독립 씬

`RankingClient.cs`는 이름·점수 입력, 등록·조회 버튼, 상태 글자와 랭킹 글자를 연결한다. 정상 등록 뒤에는 랭킹을 다시 조회한다. 등록은 성공했지만 후속 조회가 실패하면 두 결과를 구분해 표시한다.

- 요청 중에는 버튼을 잠그고 `finally`에서 복구한다. 네트워크 제한 시간은 15초다.
- JSON을 보내는 POST에는 `application/json`을 지정한다. 응답은 `scores` 배열을 가진 래퍼 클래스로 읽는다.
- 현재 클라이언트는 빈 이름과 잘못된 점수를 먼저 검사한다. 따라서 빈 이름으로 버튼을 누르는 것만으로 서버가 HTTP 400을 반환했음을 검증할 수는 없다. 서버 검증은 직접 HTTP 요청으로도 확인해야 한다.
- `RankingSceneSetup.cs`의 메뉴로 기존 씬을 덮어쓰지 않고 독립 랭킹 씬을 만들 수 있다. 저장된 `RankingScene.unity`도 추가했다.
- 현재 랭킹 씬의 `serverBaseUrl`은 `http://localhost:5000`이다. 몬스터 클라이언트의 배포 URL 변경과는 별개다.

| 공개 몬스터 API | `https://gamedataserver-yws.onrender.com/monsters` GET 결과 HTTP 200, 몬스터 5개를 확인했다. |
| 공개 랭킹 API | 같은 서버의 `/scores` GET 결과 HTTP 404였다. 랭킹 API의 배포 반영은 확인되지 않았다. |
| 서버 빌드 | 직전 커밋 검증에서 경고·오류 0개로 통과했다. 이번 문서 작업에서는 다시 실행하지 않았다. |
| 서버 회귀 검사 | 직전 실행은 동시 등록 단계에서 실패했다. 임시 서버 로그에 SQLite Error 5: `database is locked`가 남았다. |
| Unity 씬 | 직전 커밋 검증에서 클라이언트 GUID, UI 참조 6개와 `.meta` 구성을 확인했다. 이번에는 Editor 실행·화면 측정·등록·조회 검증을 하지 않았다. |

서버 명세에는 과거 회귀 검사 61개 통과 기록이 있지만, 가장 최근 실행은 실패했으므로 현재 전체 통과로 적을 수 없다. DB 잠금 오류가 났다는 이유만으로 DB Browser가 원인이라고 단정하지 않고, 동시 요청 시 DB 접근과 연결·리더 해제 시점을 조사해야 한다. 이번 TIL 작업에서는 코드를 수정하지 않았다.

남은 확인:

- SQLite 동시 등록 잠금 원인을 해결하고 회귀 검사를 다시 통과시킨다. 실패 지점 뒤의 재시작 검증도 최근 실행에서는 완료하지 못했다.
- Unity에서 실제 등록·조회·오류 표시·연결 실패·버튼 복구를 확인한다.
- 배포 대상 브랜치와 랭킹 코드 반영 여부를 확인한 뒤 공개 `/scores` 등록·조회와 다른 기기 접근을 검증한다.
- 배포 환경의 영속 저장 경로를 결정하고 재시작·재배포 후 데이터 유지 여부를 확인한다.
- 기존 `SampleScene`, `MonsterClientAsync`의 공개 URL 변경, TMP 폰트 변경은 로컬 미커밋 상태로 남아 있다. 이 TIL 업로드에 포함하지 않는다.

## 기억할 것

- 커밋은 로컬 기록, 푸시는 원격 저장소 반영, 배포는 외부 환경에서 서버를 실행하는 일이다. 단계마다 확인할 결과가 다르다.
- 같은 저장소라도 브랜치가 다르면 실행되는 기능이 다를 수 있다. 기능 브랜치에 API가 있다고 배포 서버에도 있다고 가정하지 않는다.
- 데이터 필드 이름과 응답 모양은 서버와 클라이언트의 약속이다. 강의 예제와 다르게 구현했다면 차이를 문서에 남겨야 한다.
- DB 파일이 남는 로컬 재시작과, 파일 시스템이 교체될 수 있는 재배포는 구분한다.
- 빌드 성공이나 씬의 정적 참조 확인만으로 사용자 동작까지 완료됐다고 판단하지 않는다.
